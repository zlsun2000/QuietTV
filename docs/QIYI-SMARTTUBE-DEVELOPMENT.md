# 怎样让 AI 为一个电视应用寻找续播接口

这次从奇异果和 SmartTube 的实际适配中，得到了一套可复用的方法：先确认应用肯提供什么记录，再找能打开同一内容的入口，最后用电视验证。**找到一个广播名，或者能打开播放器，都不等于已经实现续播。**

本文前半记录开发过程，后半面向开发者和使用 AI 的人。只想导入文件，请看[两份配置的使用说明](playback-rules/README.md)。核对日期为 2026-10-19。文中的事件、内容 ID 和片名均为合成示例，不包含用户账号、观看清单、私人截图、完整日志或第三方反编译代码。

## 这次是怎样找到入口的

### 1. 先分清装的是哪个应用

“爱奇艺”“SmartYouTube”只是使用者看到的名字。同名或近似应用可能来自不同渠道，接口完全不同。

| 实际应用 | 本机版本 | 最初确认的事实 |
| --- | --- | --- |
| TCL 奇异果 `com.tcl.qiyiguo` | 16.9.0.221250，versionCode 221250 | 正常播放后会向桌面发送 TCL 渠道历史广播。 |
| 旧 SmartYouTube `com.liskovsoft.videomanager` | 6.17.739，versionCode 1319 | 用户能正常播放，但本机检查时没有提供标准媒体会话；本机也没有可用的系统继续观看提供者。 |
| SmartTube `org.smarttube.stable` | 32.56，versionCode 2446 | 提供视频 ID 和播放进度，另有接收内容链接及时间参数的入口。 |

所以没有把新 SmartTube 的文件冒充为旧 SmartYouTube 的适配。换用另一个客户端前，先得到设备所有者同意，并保留旧应用。这里不分发任何第三方 APK。

### 2. 先找记录从哪里来

奇异果的已安装 APK 中，播放记录观察类构造 `com.tv.history.add` 消息。静态检查核对了 `sendBroadcast` 附近赋值，再用设备正常播放后静幕收到的记录确认字段，而不是凭字段名猜。

本版本的消息结构可概括为：

```json
{
  "packageName": "com.tcl.qiyiguo",
  "videoId": "123456",
  "videoName": "合成示例剧集",
  "episodeName": "第 3 集",
  "cmdInfo": "{\"videoId\":\"123456\",\"episodeId\":\"789\",\"chnId\":2}",
  "currentPosition": 83000,
  "duration": 300
}
```

这里的 `videoId` 是剧集/专辑层面的标识；具体一集还要看 `cmdInfo.episodeId`。`currentPosition` 为毫秒，`duration` 为秒。配置交叉检查外层与内层 `videoId` 一致，避免把不同内容拼在一起。仅有剧名时，不推测集数。

SmartTube 采用另一条路径：Android 标准媒体会话提供 `MEDIA_ID`、标题、位置和时长。这个来源已经由静幕支持，因此不需要为它编造一个历史广播。

### 3. 再核对点击后怎么打开

奇异果最初使用 `com.tcl.qiyiguo.action.ACTION_DETAIL`，传递内容、集数和历史进度。用户实测部分内容确实能接着看，但后续发现：

| 内容及进入方式 | 本机观察 |
| --- | --- |
| 无广告内容，从应用或旧桌面入口进入 | 都能保存记录。 |
| 含广告内容，从应用正常进入 | 能保存记录。 |
| 含广告内容，从旧桌面入口进入 | 曾出现不再更新完整记录、只剩应用卡片的情况。 |

这说明最初的“能接着看”验收还不够，还必须检查“退出以后能否继续记录”。静态调用路径也提示详情入口和完整播放入口处理信息的方式不同。这些线索支持更换入口，不代表所有含广告内容或所有版本都存在同一问题。

最终配置改为 `com.tcl.qiyiguo.action.ACTION_PLAYVIDEO`，`playInfo` 保留明确的内容与集数，设置 `autocomplete: true`、`history: -1`。**这里由爱奇艺读取自身历史，不向它强行指定某个毫秒位置。** 因此底层为普通适配增加 `native` 能力，界面显示“按应用进度续播”。较旧集数的选择仍由原应用决定，未冒充精确指定集数。

SmartTube 则通过固定的 `SplashActivity` 接收 `https://www.youtube.com/watch?v={id}&t={seconds}`。在当前 APK 的参数读取路径核对 `t` 的处理，并检查[上游项目](https://github.com/yuliskov/SmartTube)对应的入口和播放控制流程；最终以实际安装版本为准。路由限定目标包、版本和签名，不把整条任意链接透传给系统。

### 4. 用真实播放验收，再补失败场景

实测环境：雷鸟 50F295C-JN、Android 9，个人测试版静幕；不是在这台电视重新验收的公开稳定 APK。

- 奇异果：完整入口约从 13 秒继续，返回后收到 72 秒新记录；从桌面卡片再次打开约从 1:12 继续，进入下一集后收到第 2 集 10 秒记录。该证据覆盖本机含广告流程，不保证所有旧集数的选择。
- SmartTube：保存 142746 ms，关闭客户端后由桌面卡片重新启动，实际会话初始位置 142245 ms，约 2:22，并自动播放。设备所有者也自行确认通过。不把这一偏差概括为所有内容的精度保证。
- 通用会话曾与具体剧集产生重复卡片。修正为：存在有效续播入口时，显示层隐藏应用占位卡片；不删除原始记录，也不按相似标题合并进度。停用适配后仍可显示备用入口。
- SmartTube 纯链接启动时，标题可能暂时只剩应用名。仅在同一规则、同一明确内容标识匹配时保留已有完整标题，采用新进度，避免造出重复记录或覆盖另一视频。
- 更新 APK 后，本机曾出现授权仍在但系统监听未连接。排查时把“收不到任何事件”和“收到事件但字段不对”分开处理；更换续播参数不能修复权限或连接问题。

公开贡献保留相同续播字段和参数，移除了个人版联网封面声明，并提升配置 revision。公开解析器和合成路由测试另行验证；不能把个人版实机结果写成公开 APK 已完成全机型验收。

### 5. 没有发布的内容

个人版也验证了封面：奇异果消息中的 `videoImgUrl` 使用专门的图片子域，SmartTube 可按视频 ID 获取缩略图。早期仅允许另外两个图片域名，导致真实封面被拒绝。这是“接收到图片地址”和“允许下载”需要分别排查的例子。

本次没有把该联网扩展、图片、实际地址或用户截图发布。公开范围仍按[项目来源审查](LEGAL-REVIEW.md)处理，不能从“图片能下载”推导出服务访问或再分发已获授权。本文没有复刻第三方实现、分发音乐/视频、绕过广告、会员或内容保护。

## 给下一位开发者的排查方法

### 先读标准接口，再决定是否检查应用内部入口

优先检查 [MediaSession](https://developer.android.com/reference/android/media/session/MediaSessionManager) 和 [Android TV Watch Next](https://developer.android.com/training/tv/discovery/watch-next-add-programs)。先让设备所有者在原应用正常播放、暂停，再确认当前版本到底发布了哪些信息。没有读取权限和确实没有记录，应分别记录。

只在设备主人明确允许时连接 ADB。以下是调查方法，不是让维护者自动连接任何电视；设备地址由主人提供。

```powershell
adb connect <设备地址>:5555
adb shell dumpsys package <应用包名>
adb shell dumpsys media_session
adb shell pm path <应用包名>
```

这些输出可能包含私人播放信息，只在本地检查。不要把整段结果贴到公开 issue、PR 或 AI 公开分享链接中；只整理应用版本、是否有会话、字段名称和合成示例。

### 检查本人合法取得的 APK，不发布反编译实现

必要时，从自己设备上取得有权检查的安装包，在本地查看 Manifest、公开 Activity、intent-filter、Provider 和 Receiver。可使用 [JADX](https://github.com/skylot/jadx)辅助阅读，再搜索：

```text
sendBroadcast / putExtra / addRecord / history
MediaMetadata / METADATA_KEY_MEDIA_ID / PlaybackState
ACTION_VIEW / getIntent / getStringExtra / getQueryParameter
```

搜索到名字后，沿调用关系追到字段赋值和接收处理。只看到 `position`、`seek` 或 `history` 字样不算证据：它可能是内部播放器通信、下载记录或 UI 状态，外部应用未必能调用。

对每个候选接口写下这几项，再交给 AI：

| 问题 | 必须有的证据 |
| --- | --- |
| 谁发出记录？ | 目标包、应用版本、签名、真实发送路径；来源字符串本身不能认证发送者。 |
| 广播是否真的送到第三方桌面？ | 隐式、包定向或组件定向；权限和运行时接收限制；不能只读 Manifest。 |
| 怎样确定同一部、同一集？ | 明确内容 ID 与集数 ID，缺失就标明缺失。 |
| 时间是什么单位？ | 赋值/转换代码与实机进度对照，不能只凭字段名判断。 |
| 入口是否对外可用？ | 已导出、权限允许、系统可解析、目标固定在原应用内。 |
| 进度由谁决定？ | 指定秒数、应用自身历史、只打开内容，三者分别声明。 |
| 退出后还会更新吗？ | 新事件、新进度与集数，不能只检查进去那一下。 |

禁止用通知正文、账号数据库、完整日志、无障碍页面或播放流地址作为静幕的历史来源。不能为了让配置“看起来有效”去伪造内容、集数、广播或跳转参数。

### 交给 AI 的任务可以这样写

> 阅读 QuietTV 的 docs/WRITING.md、docs/PLAYBACK-RULES.md 和本文。我会提供有权检查的应用版本、包名、签名以及脱敏接口资料。先分别确认记录来源和点击入口，不预设某个广播一定存在；说明每一字段的来源、时间单位和稳定身份。优先使用标准播放信息；没有接口时明确说不能只靠 JSON 完成。只在已有适配器范围内生成有界 JSON，不添加账号、播放流、脚本、任意命令或未审查网络图片。检查目标签名和版本，制作合成事件与预期参数；没有主人授权不操作电视。先标为待实测，得到同内容、同集数、进度、自动播放及返回后更新的实际证据后，再更新验证说明。保持普通用户说明通俗，并记录失败与未验证范围。

### 最后怎样验收

先在隔离模拟器验证导入、类型、单位、目标限制、缺字段、错误版本、停用、回退和记录上限。模拟器中的合成应用不代表真正播放器已经适配。

实机至少覆盖从原应用进入、从桌面进入、播放后返回、再次点击、客户端结束后重新打开；有分集或广告差异时分别检查。不要为了测试强制停止用户正在使用的应用，或未经许可发送遥控按键、重启和截图。

贡献只包含自有配置、说明和合成样例。检查公开文件与 Git 历史，排除 APK、反编译源码、凭据、签名密钥、私人日志和观看截图。配置中的验证状态是作者提供的证据说明，不是官方支持或永远兼容的保证。
