# 静幕的写作约定

这是项目维护者的长期要求，适用于后来接手的人和 AI。换对话、换版本或增加功能时，都应继续遵守。修改项目规范时，也要保留这个要求。

**先假设读者只会用遥控器、安装应用，不懂编程。先说他能看到什么、需要做什么，再提供想了解细节的人可以点开的链接。**

## 哪些内容要通俗

README、GitHub 发布页、公开版本记录、安装帮助、隐私说明、应用里的提示，以及向项目所有者汇报工作，都使用简明中文。菜单名称、文件名和系统提示可保留原文，让用户能照着找到；陌生名称首次出现时解释用途。

构建、架构、适配规则、来源审查和测试记录可以使用准确的技术术语，但要在开头说明面向开发者。普通用户应有一份能独立看懂的说明，不用先读技术文档。

## 怎么写

- 第一段说清这是什么，或者这次解决了什么使用问题。
- 描述操作时写出实际菜单路径，每一步只做一件事。
- 优先写用户能观察到的变化，例如“退出视频应用后，原来的背景会重新显示”。
- 标题直接用“怎么安装”“升级前看这里”“安装失败怎么办”。避免把发布页写成开发周报。
- 普通发布说明通常用几条更新、几步安装和必要的限制就够了。测试数量、接口名称和完整排查命令放到链接后的资料中。
- 技术词没有直接替换词时，解释它对使用者有什么影响；不要仅把英文换成另一种难懂的中文。

| 技术写法 | 面向用户的写法示例 |
| --- | --- |
| 侧载 APK | 安装从商店以外下载的安装包 |
| 默认 HOME / HOME 路由 | 默认桌面 / 按遥控器 Home 键后打开哪个桌面 |
| 重建解码器、完成回调丢失 | 修复视频背景播完一遍后停住的问题 |
| 生命周期恢复、缓存回收 | 从视频应用返回时，重新显示原来的背景 |
| Watch Next provider / MediaSession | 电视系统提供的继续观看记录 / 播放应用提供的当前播放信息 |
| 导入 JSON 规则 | 导入应用适配文件；菜单叫“导入 JSON 规则”时保留菜单原名 |
| 同签名覆盖升级 | 直接安装新版，不用先卸载，原设置会保留 |
| 降级 / 兜底 / fallback | 具体写清结果，如“视频不能播放时显示内置图片” |
| CI、API 级别、回归计数 | 已检查安装、升级或相关功能；完整测试记录另附链接 |

这些是按场景改写的例子，不是要求机械替换。不能为了简单而改变实际行为。

## 简单也要说清的事情

- 升级能不能保留数据；卸载会删除什么。不能只说“签名冲突”就让用户自行猜测。
- 功能是否默认关闭，需要用户开启什么权限，怎么关闭或恢复。
- 联网会向谁发送什么信息，第三方服务有哪些使用条件。
- 哪些电视或应用确实测过，哪些还没有。模拟器通过不能写成所有电视可用；测试版结果不能冒充正式安装包实测。
- 续播、输入源和开机默认桌面的限制。不要为了好懂而写成必定可用。

截图必须来自真实运行界面，并说明版本和环境。没有新截图时注明现有图片的版本，不把旧图说成最新版实拍。

## 发布时怎么保持一致

1. 从 [发布说明模板](releases/TEMPLATE.md) 复制一份 `docs/releases/v版本号.md`。
2. 对照实际变化写成用户能观察到的结果，保留升级和兼容提醒。
3. 技术记录留在专门文档或版本附件，发布页只放简短说明和链接。
4. 按下面的清单审阅，把审过的文件原文作为 GitHub 发布说明。

## 提交前自查

- 不懂编程的人能说出这次改了什么吗？
- 能找到该下载的文件、下一步操作和遇到问题的帮助吗？
- 是否出现了未解释的英文缩写，或“兜底、链路、收敛、注入”等没有说明具体结果的说法？
- 技术细节是否挤在安装步骤或功能介绍之前？
- 升级数据、隐私、权限和未测试范围是否交代清楚？
- 菜单路径、版本、文件名和截图说明是否与实际一致？

这份约定需要接手者遵守和审阅，不能靠关键词检查保证所有文字都好懂。发现难懂的段落，应改写整句话，不要用同样专业的词替换。
